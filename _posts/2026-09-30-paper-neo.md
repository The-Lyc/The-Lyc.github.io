**_NEO: SAVING GPU MEMORY CRISIS WITH CPU OFFLOADING FOR ONLINE LLM INFERENCE_** [MLSYS 2025]

---

## Motivation

kv cache是制约LLM推理的batch size、gpu利用率和吞吐量的关键因素：

<img src="{{ '/assets/blog/paper-neo/image-20251216172827338.png' | relative_url }}" alt="image-20251216172827338" style="max-width: 100%; height: auto;" loading="lazy" />

现在有两种主流方法：量化(会损失精度)和offload（受PCIe带宽制约，特别是长上下文中kv cache越算越多，IO延迟增长速度高于计算延迟增长速度，gap更加明显）

<img src="{{ '/assets/blog/paper-neo/image-20251216173008484.png' | relative_url }}" alt="image-20251216173008484" style="max-width: 100%; height: auto;" loading="lazy" />

但是论文提出两个重要的observation：

- kv cache只有attention计算才用
- decode阶段attention计算是memory bound，而CPU和GPU相比正好内存带宽差异远小于计算能力差异（modern x86 server CPU vs A10G GPU
  - Computation: 1 vs. 125 TFLOPS
  - Memory bandwidth: 200 vs. 600 GB/s）

也就是说，让CPU算一部分request的attention计算，有可能做到与gpu上的request实现overlap，减轻gpu侧的kv cache显存压力

## Design

<img src="{{ '/assets/blog/paper-neo/image-20251216174226081.png' | relative_url }}" alt="image-20251216174226081" style="max-width: 100%; height: auto;" loading="lazy" />

（图中有个小错误，$$po_1$$和$$pr_1$$做完之后才能做$$ga_0$$，线性层计算和attention是串行的）

把所有当前到达的requests分到三个队列：$$Q_{prefill}$$, $$Q_{gpu\_attention}$$, $$Q_{cpu\_attention}$$

$$Q_{prefill}$$, $$Q_{gpu\_attention}$$就是在gpu上完全运行的任务，$$Q_{gpu\_attention}$$的requests需要的kv cache都放在gpu上不会被换出

$$Q_{cpu\_attention}$$的requests需要的kv cache prefill完就会放到CPU侧，attention计算放在CPU上，但是线性层仍然放在GPU上

分的依据是：

- 刚到的需要prefill的requests当然是分到$$Q_{prefill}$$
- $$Q_{gpu\_attention}$$, $$Q_{cpu\_attention}$$都是prefill完决定每个request应该分到哪个队列

每一轮，会从三个队列中挑选合适的requests到两个batch中：

- batch-0：prefill只能在这个batch，还包含能容纳的最多的ga以及少量的ca用于overlap
- batch-1：包含剩下的符合要求（不会让gpu idle）的数量的ca

整个design的策略分为6步：

#### Step 1. Initialization

初始化两个空的 batch schedule：

- **batch-0**：mostly run on GPU，包含 prefill + decode 请求
- **batch-1**：mostly run on CPU，只包含“要算 decoding attention”的请求

这一步只是明确这轮要构造的两套子批的“角色分工”。

#### Step 2. Schedule GPU decoding requests（先把 GPU-runqueue 塞满 batch-0）

尝试把 **GPU decoding runqueue** 里的请求都放进 batch-0；然后根据 GPU memory：

- 不够就 **swap out** 一些请求，直到 GPU 能 hold “all new KV cache”；
- 够用就 **swap in** 一些请求，尽量用满 GPU 空间（Maximizing GPU）

这一步本质上是：**先保证 GPU-request 这一侧的 decode 主体尽量大**（提高 batch-0 的 $$T_{l0}$$ / 吞吐潜力），并用 swap-in/out 把 GPU HBM 利用到接近上限。

#### Step 3. Schedule prefilling requests（再从 waitqueue 塞 prefill，直到 activation 撑不住）

从 **prefilling waitqueue** 里 pop 请求塞进 batch-0：

- 如果 GPU memory 够，就把新生成的 KV 留在 GPU；
- 否则就把“生成的 KV cache swap out”；
  重复，直到 GPU 已经**hold 不住这轮 batch 的 activations**（Maximizing GPU）【Jiang 等 - 2024 - NEO Saving GPU…】

关键点：这里停下来的原因不是“KV 不够放”，而是 **activations**（本轮 forward 的中间张量）到顶了。【Jiang 等 - 2024 - NEO Saving GPU…】
所以 Step 2/3 共同实现了它的原则 “Maximizing GPU”【Jiang 等 - 2024 - NEO Saving GPU…】：尽量从 GPU/CPU runqueue 和 waitqueue 里多取请求，让 GPU 段变长、可被更好地用来 cover CPU attention。

#### Step 4. Schedule CPU decoding requests（把 CPU-runqueue 分到 batch-0 / batch-1，并强行满足两条不等式）

扫描 **CPU decoding runqueue**，把请求分配到 batch-0 或 batch-1，并保持：

- $$T_{ca0} \le T_{l1}+T_{ga0}$$
- $$T_{ca1} \le T_{l0}$$

如果把某个请求放进任何一个 batch 都会破坏不等式，就跳过它留到下一轮（Balancing and hiding CPU）。

这一步就是“为什么要把少量 CPU decoding request 塞进 batch-0”：因为它在调一个“配平问题”。

- $$T_{ca1} \le T_{l0}$$：保证 batch-1 的 CPU attention 不会比 batch-0 的 GPU linear 更长，避免出现“CPU 忙但 GPU 闲”（Hiding CPU/Hiding GPU 的具体形式）。
- $$T_{ca0} \le T_{l1}+T_{ga0}$$：保证 batch-0 中那一点 CPU attention 也能被另一段 GPU 工作盖住。
  这两条就是前面推导出来“希望保证”的约束在调度层面的落地实现。

#### Step 5. Reduce prefilling requests（把“需要 swap-out 新 KV 的 prefill”尽量踢掉，以免 CPU idle）

从 batch-0 里移除那些 **会导致生成 KV 需要 swap-out** 的 prefill 请求，只要移除后仍满足 Step 4 的不等式；论文说目的是避免 CPU idle（Balancing）。

直觉：Step 3 会“尽量多塞 prefill”，但塞太多会把 batch-0 的 GPU 段拉得过长，同时 batch-1 的 CPU attention 可能并没有相应变长，于是 CPU 会在 overlap 中出现空转；此外，需要 swap-out 新 KV 的 prefill 还会引入额外传输/管理开销。Step 5 相当于对 Step 3 的贪心进行“回撤”，让两边更接近“平衡”。

#### Step 6. Make decisions（两套方案：two-batch vs GPU-only，按估计指标选）

到这里 two-batch schedule 已经构造出来了；然后再构造一个 **GPU-only schedule**：取 batch-0 并排除 Step 4 加进去的 CPU decoding requests。最后比较两者估计的 $$x/T$$，选“更大”的那个（Greed）。

核心意图是 **two-batch 不一定更好，所以必须每轮自适应地回退到 GPU-only**（尤其是你之前提到的：GPU 需要容纳两套子批导致 sub-batch 变小的情况）。
